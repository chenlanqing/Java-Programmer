## [AI 工程师技能地图](https://www.andrewng.org/writing)

###  第一项：构建和部署 AI 应用
AI 应用和非 AI 应用最大的不同，是前者输出不靠谱。你给大模型一个 prompt，回来啥样心里没底；你训了个深度学习模型，它在新样本上会预测出啥，你也不知道。传统软件好歹行为能预期。

所以会做 AI 应用的人，得懂那些积木：大模型、上下文工程、RAG、智能体工作流、机器学习和深度学习。但更关键的是，懂怎么用统计手段去度量、去引导、去约束这个系统，让它别太离谱。这里面最核心的一门本事叫 evals（评估）加错误分析循环，说白了就是别凭感觉调，拿数据说话，反复测、反复改。

###  第二项：软件工程基本功
这点他说得挺直白。你真懂软件怎么跑，才盖得好系统。做工程本来就在成本、扩展性、可靠性、速度之间来回妥协，安全隐私再加一层复杂度。

懂基本功的人，至少知道「有哪些妥协可以做」。选技术栈、设计架构、搞数据存储、写测试，决策质量都不一样。他特意点了一种现象：有些人不懂这些权衡，直接甩给编码智能体「凭感觉写」，结果智能体替他做了很多糟糕的取舍，因为他根本不知道该给智能体什么上下文。基本功扎实的人，能用工程师的精确语言去指挥智能体，而不是被它带着跑。

###  第三项：用编码智能体
现在会用 agentic coding，已经不是加分项，是基本功。会的人，脑子里有智能体怎么干活的模型，知道它短板在哪、怎么绕开，也知道什么时候插手、什么时候撒手，既不出 bug 也不瞎烧 token。

具体怎么练？管住智能体的上下文，在「规划」和「执行」之间做取舍，给它验证器或 evals 让它自己把活干完；知道什么时候该写清楚 spec、什么时候没必要费那劲；多个智能体一起干活时你怎么调度；还要躲坑，比如别让它把你的生产数据库搞挂。

还有句大实话：这玩意儿变得太快，所以「会用」不只是懂现在的先进做法，还得养成习惯，不断试新工具、跟着最佳实践改自己的工作流。

###  第四项：定义要做什么（Shaping the build）
这一项我最有感触，后面细说。吴恩达的判断是：spec 给清楚了，智能体交活越来越快。所以我们工程师的活，正在从「按图施工」往「决定图上该画啥」挪。

别再指望别人给你一版像素级的设计稿，你只管实现。有效的 AI 工程，需要你有产品感，懂业务背景、懂客户目标，能参与进去、把东西往前推。AI 也给了你比以往更大的主动权：你能自己发现问题、抓住机会、负责任地做出来。比如你得知道什么时候该快速搞个 MVP 丢给用户测，什么时候该慢下来、多花时间把东西做扎实。

> 四项底下还压着一个东西：持续学习的心态。AI 变得太快，大家只能跟着跑。

## 哪些环境使用 AI

把 AI 融入整个研发流程，但不同阶段使用方式不一样
- 需求阶段，我会让 AI 帮我梳理需求、补充边界场景和异常场景；
- 技术方案阶段，我会让 AI 从不同角度分析方案，比如性能、一致性、可扩展性以及潜在风险，但最终架构决策还是我自己做；
- 编码阶段，我会让 AI 辅助生成代码、补测试、重构以及解释陌生代码；
- Debug 阶段，我会把异常日志、调用链、关键代码和复现条件提供给 AI，让它辅助定位问题；
- Code Review 阶段，我会让 AI 做一轮静态分析，重点检查空指针、并发、事务、资源释放、异常处理等问题。

所以使用方式不是单纯让 AI 写代码，而是把 AI 放到整个研发闭环里面

### 在需求分析阶段，如何使用 AI

需求分析阶段，不会直接让 AI 根据一句需求生成代码，而是先让它帮我把需求结构化。

比如会把产品需求、接口文档或者业务规则给 AI，让它帮我拆成核心流程、业务规则、异常流程和边界条件。

比如一个订单自动关闭需求，我会让 AI 帮我分析：
- 正常流程是什么；
- 订单超时怎么判断；
- 支付和关闭同时发生怎么办；
- 重复执行怎么办；
- MQ 延迟或者消息丢失怎么办；
- 数据库更新失败怎么办。

然后结合现有系统的代码和数据库结构进一步验证。

AI 比较适合做的是‘发散’，帮我发现容易遗漏的场景；但哪些场景是真实业务要求，还是需要结合实际系统和产品确认。

这里有一个很重要的点：AI 擅长补充场景，但不能把 AI 生成的业务规则当成真实需求。

### 在技术方案设计阶段，如何让 AI 辅助？

技术方案阶段，主要把 AI 当成一个方案评审助手，而不是让它直接替我做架构设计。

比如一个百万级订单的延迟任务系统，我可能先自己确定几个方向，比如 Redis ZSet、MQ 延迟消息、时间轮，然后让 AI 分别从吞吐量、延迟、可靠性、故障恢复、运维成本几个维度做对比。

另外我会让 AI 主动找方案中的反例。

比如：
- Redis 节点故障怎么办？
- MQ 积压怎么办？
- 任务重复执行怎么办？
- 服务重启任务会不会丢？
- 数据库更新成功但消息发送失败怎么办？

这样 AI 对我最大的价值不是直接给答案，而是帮助我进行方案发散和风险检查。

最终的架构选择还是结合业务量、现有技术栈和团队能力来决定

### 编码阶段如何使用 AI？

但我一般不会直接让 AI 一次生成整个项目，而是先让 AI 理解 Repository，再拆任务。

比如我要实现一个 Spring Boot 接口，我通常会先让 AI 找相关 Controller、Service、DAO、DTO，以及类似功能的实现，然后先给出修改计划。

确认方案以后，再让 AI 按模块修改代码。代码生成以后，我会让 AI 补充单元测试和边界测试，然后实际运行测试。

最后通过 Git Diff 检查具体修改了哪些文件。

所以我的流程基本是：Repository Understanding → Plan → Coding → Test → Review。

复杂任务我会进一步拆成多个小任务，避免一次给 AI 太大的上下文。

### Code Review如何使用 AI？

一般把 AI Review 作为人工 Code Review 之前的一层辅助检查。

比如我会让 AI 重点检查几个方面：
- 第一是正确性，比如空指针、异常处理、边界条件；
- 第二是并发问题，比如锁、线程安全、重复执行；
- 第三是数据库问题，比如事务范围、慢 SQL、索引使用；
- 第四是资源问题，比如线程池、连接池、文件句柄；
- 第五是代码设计，比如重复代码、职责不清、过度耦合。

但是 AI Review 不能替代人工 Review。尤其是业务逻辑、一致性要求、架构设计和安全风险，最终还是需要开发人员负责。

所以我的理解是：AI Review 负责发现问题，人负责判断问题。

### 使用 AI 的时候 Prompt 一般怎么写

Prompt 一般不会只描述我要什么，而是会明确 Context、Goal、Constraint 和 Output。

比如让 AI 修改一个 Java 模块，我通常会告诉它：
- 当前项目是什么；
- 相关模块和代码在哪里；
- 我要解决什么问题；
- 有哪些技术约束；
- 哪些代码不能修改；
- 希望最终输出什么。

例如：‘这是一个 Spring Boot + MySQL + Redis 项目，现在需要优化订单查询接口。请先分析现有代码，不要直接修改。重点关注 SQL、索引、Redis 使用和并发问题。先给出问题分析和修改计划，确认后再修改代码。’

对于复杂任务，我会采用多轮 Prompt，而不是一次性把所有事情交给 AI。

可以总结成：Context + Goal + Constraint + Expected Output

### 如何给 AI 输入？

我会根据任务给 AI 不同类型的上下文。
- 比如做代码修改，我会提供相关源码、项目目录结构、接口定义、数据库 Schema、配置以及类似功能的实现。
- 如果是 Debug，我会提供异常堆栈、日志、调用链、请求参数以及复现步骤。
- 如果是方案设计，我会提供业务目标、QPS、数据量、SLA、技术栈以及约束条件。
- 我不会把整个 Repository 不加筛选地全部塞给 AI，因为无关代码太多反而会污染上下文。

所以我比较关注的是 Context Engineering，也就是根据任务选择真正相关的上下文

## 如何判断 AI给出内容是否正确？

我不会直接相信 AI 的结论，而是通过几个层次验证。
- 第一层是逻辑验证，看方案是否满足业务需求和边界条件；
- 第二层是代码验证，看实际实现是否符合现有架构；
- 第三层是测试验证，包括单元测试、集成测试和异常场景；
- 第四层是工程验证，比如执行 SQL 的 EXPLAIN、压测、线程 Dump、监控指标等；

如果是生产问题，还要结合真实日志和监控数据。

比如 AI 告诉我某个 SQL 加索引可以解决慢查询，我不会直接采用，而是会先看执行计划、数据分布和实际耗时，确认优化前后的效果；

## 如何保证 AI 生成的代码质量

“我一般通过‘限制生成范围 + 自动测试 + 人工 Review’三个方面保证质量。

第一，限制生成范围：不会让 AI 一次修改几十个模块，而是把任务拆成小的、可验证的修改。

第二，自动验证：代码生成以后必须编译、跑单元测试和集成测试，有条件的话还会进行接口测试或者压测。

第三，人工 Review：重点检查业务逻辑、事务边界、并发、安全、异常处理和性能。

另外我会通过 Git Diff 控制 AI 的修改范围，如果发现 AI 修改了与任务无关的代码，会直接回退。

## 工程能力

从码农到工程师：永不失业的秘诀。

- 什么是码农？就是单纯写代码的人。当 Agent 可以生成代码的时候，码农的价值就会被替代。
- 什么是工程师？是能够设计并驾驭复杂系统的人。工程师的核心能力不在于写代码，而在于：
- 理解系统的复杂性
- 抽象和结构化思维
- 驾驭不确定性

## 如何拆分任务

面对体量大的任务，要拆，怎么判断该不该拆？两个标准：
- 标准一：生成的代码量是否超出你一次能 review 的范围。十几行代码，肉眼扫一遍就行，不用拆。几十个文件、几百行配置，一次看不过来，必须拆；
- 标准二：步骤之间是否有依赖关系。如果第二步依赖第一步的结果（比如业务模块的 pom 依赖公共模块的 pom），那就应该先完成第一步、验证正确，再做第二步。否则第一步错了，第二步会错得更离谱；

> 先地基，后框架，最后验收

## 方法论

### 哪些代码该给 AI 写，哪些自己把关

1. 适合给 AI 写的：有规范、有模式、有标准答案的代码  
CRUD 接口、适配器、DTO 转换、工具类、配置类、测试代码，这类代码逻辑清晰，有套路可循。AI 写出来和有经验的程序员写的差不多，而且更快。Hify 整门课 80%  以上的代码属于这类，全部放手给 AI

2. 不适合给 AI 写的：需要深度判断、没有标准答案的代码  
架构设计、核心数据模型的取舍、安全边界的划定、性能瓶颈处的核心逻辑，这类代码 AI 能写出来，也能跑，但方向可能是错的，而且你不一定能从代码本身看出来。错的方向比写错的代码危险得多，因为它表面上没问题

核心链路、核心功能、核心模块等这些是要把关的地方，也是 review 和测试的重心所在

### Review：按核心链路看，双模型互补

核心链路 review 才是正确姿势；

双模型互补：比如 Claude Code 写完核心模块，把代码喂给 ChatGPT review。两个模型训练方式不同，盲点不同，互补效果很好
```
你是一位有十年经验的 Java 后端工程师，正在做代码 review。
以下是 xxxx 链路的核心代码，请从这几个维度给出意见：

1. 安全性：权限校验是否完整，有没有越权访问的可能
2. 静默失败：有没有 catch 块吞掉了异常，调用方感知不到失败
3. 边界条件：null 处理、空列表、并发场景有没有遗漏
4. 性能隐患：N+1 查询、不必要的阻塞调用、大对象

不需要夸代码写得好。直接说问题，每个问题给出具体位置和修复建议。

代码如下：
[粘贴核心链路代码]
```

### 单测边界：先问该不该测，再问怎么测

- 值得写单测的：输入固定输出就固定、不依赖任何外部系统
- 不值得写单测的：核心是外部调用的代码


## Agent 岗位

### Agent 工程化能力

#### 具备 Claude Code、Cursor、OpenClaw 等 AI 编程工具的重度使用经验

不光要会用 Claude Code 写代码，还得知道它内部是怎么拆解任务的、上下文是怎么管理的、工具调用的 schema 是怎么设计的。

能接入 LangChain、OpenAI Agents SDK 这些外部框架，还要能做 Agent 的容器服务、运行时环境、轨迹回放和调试分析。

Claude Code、Codex 这些 Coding 工具，你得能说清楚它们在哪些任务上强，怎么改 prompt、改上下文、改工具链

#### 其他

Docker、Kubernetes、CI/CD、Git 工作流、代码审查

### 模型机制理解

#### 理解 Context Window 和 Token 机制

- 上下文为什么会爆？
- 工具 schema 为什么占 token？
- 多轮对话怎么压缩？
- 长上下文对 Agent 可靠性有什么影响？

这些问题直接决定了 Agent 在长任务中的可靠性

### Tool Use、Function Calling 和 MCP

- 你能不能定义稳定的工具接口？
- 能不能设计参数 schema？
- 能不能处理工具返回的各种格式？
- 调用链怎么做观测？
- 失败了怎么重试？
- 权限怎么隔离？
