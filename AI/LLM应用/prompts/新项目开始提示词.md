## github 项目评估维度

| 看什么 | 具体怎么看 | 危险信号 |
| ---- | ---- | ---- |
| 活跃度 | 最近 90 天的提交分布、发版节奏 | 只剩机器人在 bump 依赖；README 还写着 alpha，两年没动 |
| 维护结构 | 贡献者的提交占比，也就是 bus factor | 九成提交来自同一个人，项目存续高度依赖单一维护者 |
| issue 健康度 | open / closed 比例、新 issue 的首次响应时间 | 几百个 open 无人回复，或被 stale bot 批量自动关闭 |
| 许可证 | LICENSE 文件本身，以及它有没有被改过 | AGPL‑3.0、SSPL、各种 source available，商业闭源场景先问法务 |
| 依赖体量 | 传递依赖数量、有没有已知 CVE | 为了 200 行的需求引入 1200 个包 |
| 部署形态 | 有没有 Dockerfile、配置能否全部外置 | 配置写死在代码里，改行为必须改源码 |
| 扩展点 | 有没有 plugin、hook、webhook 这类口子 | 想加个功能就得动核心，等于注定要长期 fork |
| 数据可迁移 | 有没有完整的导出能力 | 数据仅存于私有格式，无法导出迁移 |

许可证一栏需要单独说明，因为它是表中唯一一个事后发现就难以补救的维度。MIT 和 Apache-2.0 的使用限制最少，后者还额外提供显式的专利授权。GPL 系的传染性取决于分发方式。AGPL-3.0 将「通过网络提供服务」也纳入分发范围，对 SaaS 场景而言，这一条直接决定自有代码是否必须开源。此外还有一层容易被忽略：许可证会变更。Grafana 在 2021 年从 Apache-2.0 转为 AGPL-3.0，Redis 在 2024 年从 BSD 改为 RSAL 与 SSPL 双许可，并因此催生了 Valkey 这个分叉。选型时一并查看项目的许可证历史，是必要的

## 提示词

我要做一个 <一句话说清要什么，包括给谁用、大概多少数据量>。

先不要写代码。

请到 GitHub 上找能直接使用或二次开发的开源项目，硬约束如下：
- 技术栈偏好 <语言 / 框架>，部署环境 <单机 Docker / K8s / Serverless>；
- 许可证要求 <能否接受 AGPL、是否用于商业闭源>；
- 不可妥协的能力 <2 到 3 项>。

对每个候选项目，请给出：仓库链接、star 数、最后一次提交日期、许可证、
维护者数量、部署方式，以及「我的哪些需求它已经做了、哪些没做」。
无法确认的信息请标注为推测，不要编造。

最后给出结论：直接用 / 基于它改 / 自己开发，三选一，说明理由，
并给出最小可用版本的方案，以及第一步我该做什么。

等我确认后再动手写代码。
